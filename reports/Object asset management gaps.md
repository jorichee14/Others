# Object retrieval and asset management: literature and open gaps

Verdicts rest on abstracts and search summaries; arxiv.org could not be opened from the research session. Read the full papers named here before claiming novelty.

## Current literature

**Open-vocabulary object retrieval in robot maps is mature and active.** ConceptGraphs and HOV-SG build open-vocabulary 3D scene graphs from posed RGB-D images ([ConceptGraphs](https://concept-graphs.github.io/assets/pdf/2023-ConceptGraphs.pdf), [HOV-SG, RSS 2024](https://www.roboticsproceedings.org/rss20/p077.pdf)). Newer systems track masks before fusing them ([TRACKGRAPH](https://arxiv.org/abs/2609.31005)), keep small objects as separate instances and decide when a queried object is absent ([OVIP-SG](https://arxiv.org/abs/2608.17633)), and couple memory with search actions ([Searching in Space and Time](https://arxiv.org/pdf/2511.14004)). Objects are stored as point clouds, masks and embeddings, not as 3D assets.

**Generated object assets for simulation and manipulation exist, as one-shot pipelines.** SceneComplete turns one RGB-D view into object meshes with foundation models and raises pick success in clutter from 36.7 % to 73.3 % ([SceneComplete](https://lacuna.tiptreesystems.com/work/scenecomplete-open-world-3d-scene-completion-in-cluttered)). DreamUp3D completes occluded objects from a single RGB-D image ([arXiv 2402.16308](https://arxiv.org/pdf/2402.16308)). SimRecon (CVPR 2026) builds simulation-ready scenes from video by generating each object as an asset, scored with Chamfer distance on 20 ScanNet scenes ([arXiv 2603.02133](https://arxiv.org/pdf/2603.02133)). SAM 3D has been used to place generated objects in Isaac Sim in an industry blog, not yet in a peer-reviewed robotics evaluation ([Marvik](https://www.marvik.ai/blog/generating-3d-assets-for-digital-twin-robotics-environments)).

**Object maps that persist across sessions are a 2026 research front.** OASIS-Map matches objects across revisits and detects appeared, disappeared and moved objects ([arXiv 2607.14899](https://arxiv.org/abs/2607.14899)). LT-Mem (IROS 2026) keeps object identity and event histories over time ([arXiv 2608.19059](https://arxiv.org/abs/2608.19059)). PBD-AG stores object changes as events against a stable baseline ([arXiv 2608.10449](https://arxiv.org/pdf/2608.10449)). REACT keeps updatable object nodes with multi-view instance memory ([arXiv 2503.03412](https://arxiv.org/pdf/2503.03412)). None of them keeps a 3D asset per object.

**The MIT SPARK scene-graph line is the closest robotics work.** Hydra-Multi (IROS 2023) merges 3D scene graphs from a heterogeneous robot team online, reconciling object nodes across robots with robust optimisation ([arXiv 2304.13487](https://arxiv.org/pdf/2304.13487)). Khronos (RSS 2024) keeps each object as measured surface fragments and reasons about when each object was present or absent over time ([arXiv 2402.13817](https://arxiv.org/pdf/2402.13817)). Hydra++ (2026 preprint) adds learned object shape estimation to the scene graph in real time, with CRISP as the default estimator and slower estimators, SAM 3D among them, evaluated as plug-in alternatives; it rejects bad shape predictions with a reprojection-mask consistency check and supports a LiDAR-camera configuration ([arXiv 2607.09455](https://arxiv.org/abs/2607.09455), [project page](https://hydra-plusplus.github.io/)). Its stated motivation is that scene graphs model objects only as partial point clouds or class-level CAD templates.

## Open gaps

| Gap | Closest work | Why it is still open |
|---|---|---|
| Complete, textured, simulation-ready assets kept in a scene graph that persists across sessions and robots | Hydra++ (complete object shapes in the scene graph); Khronos (objects over time, measured fragments); Hydra-Multi (multi-robot graph merging); SimRecon, SceneComplete (textured assets, one-shot) | Hydra++ already places SAM 3D shapes in a scene graph, but within a mapping run as far as the abstract says, and whether texture is kept is unconfirmed; Khronos tracks measured fragments, not complete assets; Hydra-Multi merges object nodes, not assets. No work found keeps a textured asset per object and updates it as objects move, change or are seen by another robot. |
| Generated assets checked per surface against the robot's own metric measurements, with measured and generated parts labelled | Hydra++ accepts or rejects a whole predicted shape by a 2D reprojection-mask check; SimRecon scores against reference meshes; SceneComplete reports grasp success | Checks are per object and in the image, or offline against a reference. None measures each surface against LiDAR or depth and records which parts are real, which a planner, a simulator or a radio model would need. |

## What this means for the planned pipeline

SAM 3 masks with measured point clouds remain the right source for where an object is and how to grasp it. SAM 3D assets, generated on the server at metric scale from the measured point map, are the contribution: kept in a registry with the object map, updated across sessions, and each one checked against the measured cloud with its generated back side labelled. Hydra++ is the work to build on and compare against: it already puts estimated shapes, including SAM 3D's, into the scene graph with a LiDAR-camera option. Using SAM 3D in a robot map is therefore not new by itself; its full text, especially the shape-estimator comparison, must be read before the pipeline is designed. The contribution beyond it is textured SAM 3D assets kept across sessions and robots, each checked surface by surface against the measured cloud. That combination was not found in the literature.
