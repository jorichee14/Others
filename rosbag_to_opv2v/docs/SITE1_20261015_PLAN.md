# Plan: coop site_1 20261015 as one dataset for InCoP, OpenCOOD and the heterogeneous arms

The bag: `work/20261015/coop/site_1/mirc_dataset_coop_site_1_20261015_merged_final`
(329 s, 75 topics, poses and TF from the pipeline). Both robots carry an Ouster
(mobile_1 OS1-64, mobile_2 OS1-128); mobile_1 has the ZED (420 frames, 1.3 Hz),
mobile_2 the RealSense colour (4487 frames, 15 Hz); infra_1 a camera and a radar.

## Decisions

| | Decision | Why |
|---|---|---|
| Layout | OPV2V tree, agent folders `0` (ego) and `1`, scenario `case_0`, root name ending `_real_world` | InCoP's loader fixes ego 0, order [0, 1], max_cav 2, and reads BEV handedness from the path; OpenCOOD takes the smallest non-negative id as ego, so the same tree serves both and Where2comm, CoBEVT, V2X-ViT, CGRF in the fork |
| infra_1 | off | 49 radar points do not survive a LiDAR branch; a third folder breaks InCoP's two-agent assignment. A 3-agent OpenCOOD tree is one more run of the same config with it on, later, if wanted |
| Ego | decided by the Stage 0 check, not declared | both robots see 360 deg now; the collaboration signal is occlusion and range. `label_static.py --check` gives per-agent visibility; the ego is the one that sees the objects alone less often. Default mobile_2 (as in coop2) until the check says otherwise |
| Poses | each robot's pose topic from stage 10 with the cloud extrinsic that cancels the chain, so every cloud lands at its stage 04 registered LiDAR pose | mobile_1: `/mobile_1/camera_pose` (ZED left optical) with the coop2 extrinsic (same `/tf_static`, same numbers). mobile_2: `/mobile_2/camera_pose` (colour optical, derived from the LiDAR trajectory through the rig calibration) with the inverse of that same calibration: the untrusted calibration cancels exactly for the LiDAR; only the camera's own pose keeps its 8 cm / 1.6 deg error, which is stated |
| Frame grid | master mobile_1 Ouster, 10 Hz, tolerance 55 ms | two free-running 10 Hz LiDARs have a fixed phase offset anywhere in 0..50 ms; 40 ms can drop every frame, and the converter refuses anything under the 50 ms structural floor |
| Clock | `verify`, reference mobile_1, max residual 10 ms | every node reported |offset| under 0.1 ms in this pass |
| Deskew | on, per-point `t` | the bag's clouds are raw sweeps |
| Ground lift | 0, floor z recorded in the yaml | fine-tuning indoors with the `mirc` preset; the OPV2V lift only matters for zero-shot OPV2V weights |
| Static labels | `label_static.py` on `mapping/cloud_in_ref_coop_site_1_20261015.pcd`, InCoP class names where they fit (`chair`, `trash_can`, `fire_extinguisher`, `potted_plant`), the rest named honestly and mapped later | one pose per object for the run, projected into every frame of both agents |
| The robots as objects | `object.emit: true` on both, cart + operator as one box, `obj_type: robot` | the only moving objects, labelled for free from the poses. The InCoP class map gets `robot` as id 7 if its loader takes an 8th class, else the OpenCOOD view uses them and the InCoP view filters them (decided at Gate 3) |
| Splits | site_1 whole as train, site_2 whole as validate; the last tenth of site_1 as the development slice; the within-site time split as a second column | the cross-site number is about the method, the within-site one about the room |

## One conversion, two views

A configured camera counts towards frame completeness, so the ZED's 1.3 Hz
would cut any tree it is required in to about 420 frames. The ZED is therefore
an optional camera (`required: false`): the full tree keeps every frame on the
LiDAR grid and says per frame whether the image is there, and the camera arm's
tree is the view of the frames that have it, same keys, same poses, same labels:

    python3 scripts/make_view.py --root <root> --out <root>_zed --require-image 1:0

| View | Frames (expected) | Serves |
|---|---|---|
| `site1_20261015_real_world` | ~2 900 (bounded by mobile_2's 3 022 scans) | LiDAR-only, L64 + L128 heterogeneous (sidecar `--assign 0=m1 --assign 1=m2`), camera(mobile_2) + LiDAR(mobile_1) |
| `..._zed` (view) | ~420 | camera(mobile_1 ZED) + LiDAR(mobile_2) |

Every model is validated on the full validate set where its sensors allow and
on the zed view's frames; the second column is the only one where a LiDAR-only
model and the ZED model are scored on identical frames.

## Poses from base_link, extrinsics from TF

Stage 10 publishes `/<robot>/global_pose` as the robot's base link in map
(`mobile_1_base_link` = `zed_camera_link`, `mobile_2_base_link` =
`camera_link`), and every sensor hangs below it on `/tf_static`. The config
names `pose.frame` and each sensor's `frame_id` with `extrinsic: tf`; the
converter composes the chain and records it. mobile_2's chain runs through the
untrusted camera-to-LiDAR calibration, but its pose topic was derived through
the same chain, so the cloud lands at its stage 04 pose exactly; only the
camera's own pose keeps the ~8 cm / 1.6 deg error.

## The link in every frame

`comms.streams`: each robot's Wi-Fi status (nearest, 1 s), ping (1 s window:
n, RTT median and p95, delivery ratio), iperf up/down (nearest, 10 s), NTP
status (nearest, 2 s), and the sniffer's two CSI links (1 s window) into every
agent's yaml; the full-rate tables as `<root>/comms/train/case_0/*.csv`, and the pipeline's
comms folder (CSI H per subcarrier, summary.json) copied beside them as `tables/`.

## Splits: train on site_1, validate on site_2

Site_1 converts whole as `train`; site_2 as `validate` with the same config
shape. The development slice for early stopping is the last tenth of site_1's
time range, cut in the trainer, never site_2. The within-site time split of
site_1 is kept as the second column: its gap to the cross-site number is the
memorisation measurement. Object classes must exist in both sites; the robots
(`obj_type: robot`) are the one class guaranteed in both.

## Labelling the static objects

Each site has five hand-labelled boxes in the map frame -- two chairs and three
potted plants -- which the converter writes into every frame of every agent.
They are the only ground truth here that no robot's own pose produced, so
"do both agents' returns fall inside them" is a real test of the extrinsics,
the anchoring and the frame timing at once.

**The recipe, both sites.** One pass over the coop cloud (`09`'s
`cloud_in_ref_<tag>.pcd` -- the run's own returns, carving-only dynamic
removal, never the `_with_ref` one, which cannot tell what the run brought into
the room from what was always there):

    python3 scripts/to_ply.py --pcd <cloud>.pcd --out ~/site.ply   # click seeds
    python3 scripts/label_static.py --pcd <cloud>.pcd \
        --floor-traj <04>/traj_<machine>_lidar.tum \
        --out <labels>.json --radius 0.4 --max-wall-contact 0.5 \
        --obj-type chair --seed=X,Y --name chair_1 ...

`--radius 0.4` bounds the cluster so a cart or a wall beside the object cannot
join it; `--max-wall-contact 0.5` is the same guard against the wall behind it.
No `--ceiling` override and no `--floor-z`.

**The floor is the whole difficulty, and it does not come from the cloud.**
The floors here are polished granite: near-specular, so they return strongly
only at normal incidence. Beside a chair at site_2 the floor has 1 032 returns
over 12 m2 -- about 80 points per m2 in a cloud of 4.6 M -- while the chair's
own seat has 14 268, and the floor's mirror images below it another 1 410. Any
density vote picks the seat or the ghost. Measured four ways, one flat floor
gave -0.395, -0.870, -1.045 and -1.320 m.

So the floor comes from the robot: it rolls on it, and its pose is registered
to 1.4 cm. `--floor-traj` takes the nearest pose's height less the sensor's
height above the ground, the latter measured under the path itself where the
floor IS at normal incidence (`statics.sensor_height`, ported from
`scoop_pipeline/datasets/lod3dgs.py`, which fills a floor for the Sionna mesh
the same way). It reads a ring 0.45 to 1.4 m from each pose and further than
0.45 m from the PATH, because the robot's own deck rides a fixed distance
under its sensor and smears along the whole track -- measured without that
exclusion the deck passes for the floor, and it is a constant offset, so
nothing downstream looks wrong.

Three traps, all of which cost a round here:

- `--floor-z` DISABLES the per-object floor (`label_static.py`, the
  `args.floor_z is None` guard). It is for a cloud whose floor has been cut
  away (`to_ply.py`'s output), not for the pcd.
- the cloud's global histogram mode is the dominant floor of the WHOLE cloud,
  which spans 56 x 62 m and more than one level. Site_2's is -0.870; the area
  the objects stand in is -0.40. Site_1's is -0.697 against -0.49 in the
  plants' corner.
- the sanity number is the sensor height, not the floor: mobile_1's Ouster
  rides 0.88 m up, the same at both sites. A floor that puts it at 1.3 m is
  wrong whatever the histogram says.

**Objects both sites see are fitted once, from both clouds.** The three plants
stand in the overlap of the two passes and did not move. Fitted per site they
came out 0.09 to 0.26 m apart, not from anchoring (their z agreed to 1 mm) but
because each pass saw a different side: site_1 had 2 to 4 times the returns.
Cropping both clouds to that corner and fitting once gives a single box per
plant, written identically into both label files, so a detection difference
between train and validate is the model's and not the label's.

**Verification, all three.** `--check` counts, per agent and per frame, the
returns inside each box (the number that decides); `show_labels.py` draws the
boxes into the robots' camera images; `labels_to_ply.py` draws them into the
cloud they were fitted in, each box's colour on both its edges and the points
it holds. A box right in one robot's frames and wrong in the other's is an
anchoring or calibration question, not a labelling one.

Where it ended (points inside, in the map cloud):

| | site_1 | site_2 |
|---|---|---|
| chair_1 / chair_2 | 4 459 / 3 920 | 4 484 / 4 219 |
| potted_plant_1/2/3 | 5 367 / 4 403 / 1 932 | 2 187 / 1 178 / 740 |

Per frame, every box is seen by both agents at both sites. Three are thin on
the second robot -- site_2's potted_plant_2 (median 4 points) and
potted_plant_3 (seen in 2 frames of 45), site_1's potted_plant_3 (7) -- so
report the plant class with its point counts beside it: a weak AP there is
coverage, not the model.

## QA gates, in order

1. **Inspect.** `inspect_bag.py --bag ... --sample 200`: topic rates, the TF
   edges `os_lidar_mobile2 -> camera_color_optical_frame` and the ZED chain,
   NTP topics. The mobile_2 cloud extrinsic is derived from that edge and
   checked by a unit test like `test_mirc_extrinsics_match_the_published_transforms`.
2. **Dry run.** `convert_rosbag.py --dry-run`: frame count near 2 900, dropped
   frames by reason near zero, no `missing:` runs longer than a second, the
   tightness curve's floor at 50 ms. `expected_start` on both pose topics
   against stage 03's `session_anchor.json` (ZED at [0.4825, -0.0627, 0.2035],
   RealSense at [-24.418, -0.026, 0.292], tolerance 0.25 m).
3. **Convert, validate.** `validate_opv2v.py --root <tree>/train --with-open3d`
   and the same for validate: every frame has both clouds, both yamls, the
   image where configured; the clouds from the two agents overlap on the walls
   when placed by their yaml poses (the extrinsics and anchoring test).
4. **Labels.** The recipe and its traps are above, under "Labelling the
   static objects". The gate: `label_static.py` frame check (the cloud is in
   the dataset's frame), fit each object, then `--check` -- both agents'
   returns land in the boxes, with the per-agent visibility table. This is also
   the ego decision and MIRC's Stage 0 gate: the ego must see the objects alone
   in clearly fewer frames than the partner.
5. **Loaders.** `validate_opv2v.py --with-opencood` through an InCoP-fork
   `mirc` config and through stock OpenCOOD: both build their dataset over the
   tree and read a batch. Sidecars present; `chair` is class 1.
6. **Record.** Frame counts per split and tree, the dropped-frame reasons, the
   ego decision and its numbers, the label list with classes, and the
   tolerance go into `RESULTS_coop_site_1_20261015.md` next to the survey's.

Site_2 repeats the same config with its paths; its tree is the held-out site.
