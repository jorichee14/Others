# InCoP → OPV2V port: running CGRF and Where2comm through the impairment matrix

**Goal.** Put two more algorithms through the same impairment sweep as the seven baselines:
**CGRF** (`ours` — Complementarity-Guided Residual Fusion, from
[`jorichee14/incop_analysis`](https://github.com/jorichee14/incop_analysis)) and
**Where2comm**, both on OPV2V, with **CoBEVT** as a cross-codebase calibration bridge.

Decisions taken (2026-08-21): **LiDAR-only first**, multimodal as a second arm; the OPV2V
**train + validate splits still need downloading** — only `test` is on disk.

---

## Why this is a small port

InCoP is HEAL-based, and HEAL is OpenCOOD-based, so the machinery the parent study depends
on is already there:

| What the sweep needs | Status in InCoP |
|---|---|
| `retrieve_base_data` to monkeypatch | ✅ `OPV2VBaseDataset.retrieve_base_data` — `commchannel` attaches unchanged |
| OPV2V dataset support | ✅ `build_dataset` asserts `dataset in [... 'opv2v' ...]` |
| A non-Isaac encoder path | ✅ `_find_encoder_class_isaac` (`heter_encoders_isaac.py:94`) **falls back** to the generic `_find_encoder_class`, so `core_method: point_pillar` just works |
| LiDAR-only operation | ✅ the model branches on `sensor_type != "camera"`; `lidar` takes the LiDAR path |
| Homogeneous agents | ✅ `assignment_path: null` — modality assignment is optional |
| An anchor-based head matching the baselines | ✅ `head_type: anchor_based` emits `cls_preds` / `reg_preds` / `dir_preds` |
| Bandwidth interception | ✅ `_run_fusion` calls `fusion_net(feature, record_len, ...)` with `feature` agent-stacked `(L,C,H,W)` — the same shape as F-Cooper/V2VNet, so one registry entry covers all five fusion methods |
| Byte-level message accounting | ✅ `CommunicationStatsMixin` already meters it |

**The whole overlay is therefore: configs, plus one loss file.** No model code is rewritten.

Two things InCoP does not ship:

- `point_pillar_loss.py` — it has only `center_head_loss`. Needed for `anchor_based`.
  `install_overlay.sh` copies it from an OpenCOOD/HEAL checkout. Fallback: generate with
  `--head center_head` and skip the port, accepting a different detection head from the
  baselines.
- OPV2V configs — generated by `make_opv2v_configs.py`.

## Files here

| File | What it does |
|---|---|
| `make_opv2v_configs.py` | Emits `single_m1_pointpillar.yaml` + one YAML per fusion method. A generator, not four hand-maintained YAMLs, because near-identical configs drift and a drifted config is an unattributable result. |
| `install_overlay.sh` | Copies the loss file, runs the generator, prints the run order. |

Plus, on the parent study side, `commchannel/feature_hooks.py` now registers
`HeterModelBevfusionHighresIsaac` for bandwidth quantization.

## Quick start

```bash
./install_overlay.sh ~/incop_analysis ~/cpfa/data/OPV2V ~/cpfa/OpenCOOD
```

Then follow the run order it prints.

## CGRF's density gate must be re-estimated for OPV2V

`ours` = **CGRF** (Complementarity-Guided Residual Fusion), InCoP's own method — see
`incop_analysis/README.md` and the class `ComplementarityGuidedCLCFusion` in
`opencood/models/fuse_modules/ours.py`. Two mechanisms:

- **DCG**, a density-conditioned gate: `Q_k = clip(log(1 + D_k) / q95, 0, 1)` per BEV cell,
  and `M_k = 1[Q_k > 0]` hard-filters the encoder output *before* cooperative fusion. This is
  where CGRF's bandwidth saving comes from.
- **CLC**, Complementary Local Correction: the ego feature is the prediction anchor and
  partner features enter **only** as an additive local residual through directional Swin
  cross-attention, with output-projection init gain 0.01 — so at initialisation the model is
  effectively ego-only and learns a correction on top.

Two porting traps:

1. **`lidar_support_mask` lives at `model.args`, not inside the fusion block.** The model does
   `encoder_args.setdefault("lidar_support_mask", args.get("lidar_support_mask", {}))`, so
   omitting it silently gives `{}` → gate off → **you are running the dense-CLC ablation, not
   CGRF**. The generator emits it for `ours` only. (This was wrong in the first version of the
   generator and is fixed.)
2. **`log_density_q95` is dataset-specific.** InCoP's `3.7377` (= log 15) was estimated on 512
   evenly sampled *indoor hospital* sweeps. Outdoor OPV2V LiDAR density is a different
   distribution, so the gate is miscalibrated until re-estimated: take the 95th percentile of
   `log(1 + D)` over sampled OPV2V **train** sweeps and pass `--dcg-q95`. Too low and
   everything passes, degenerating CGRF toward dense CLC; too high and the mask starves fusion
   of partner evidence. The generator warns loudly when the default is used.

### A prediction the sweep can test

Because partner information can only *add* to an ego anchor, and the residual is initialised
near zero, CGRF is **structurally floor-protective**: degrading a partner should shrink or
misdirect the correction rather than corrupt the ego evidence. Compare F-Cooper, whose maxout
discounts nothing and was worst under every content impairment in the parent study.

So the pre-registerable expectation is that **CGRF resists crossing the ego-only floor, and
its failure mode appears as lost gain rather than net harm.** Its specific vulnerability
should be the impairments that corrupt the *gate* rather than the features: `M_k` is computed
from the partner's own point density, so under pose error or staleness the mask is built on
geometrically wrong data and passes cells that are no longer valid. That is the parent study's
fusion-mechanism principle — each mechanism's weakness is the impairment that mimics evidence
it was trained to trust — applied in advance.

## The real cost: training

There are **no OPV2V checkpoints for CGRF or Where2comm anywhere** — not in
`incop_analysis`, not in CoAlign's zoo, not in HEAL's. The parent study's
evaluate-pretrained-only discipline does not survive into this work.

Prerequisites, in order:

1. **Download the OPV2V train + validate splits** (~100+ GB beyond the test split already
   on disk). Same source as the test data.
2. **A second conda env.** InCoP is torch 2.4.1+cu121 per its `requirements.txt`; the
   parent stack is torch 1.13.1+cu117 / spconv-cu117 2.3.6. Two `opencood` packages cannot
   be importable in one process, so the InCoP sweep runs as its own process against its own
   env. This is the same one-process-per-method discipline the parent study already uses,
   applied one level up.
3. **Train**: single-agent → cobevt → where2comm → ours. `batch_size: 2` is the default for
   a 12 GB card at OPV2V's 281.6 m range; raise it if there is headroom.

## The comparability problem, and the fix

The seven baselines are OpenCOOD checkpoints whose APs reproduce published numbers to
±0.001. CGRF and Where2comm trained here are a different codebase, backbone stack, and
training recipe. **Absolute AP is therefore not comparable across the two sets** — reporting
`ours` next to `cobevt` from the parent sweep as if they were measured the same way would be
wrong.

Two mitigations, both cheap:

1. **Report NPD and floor-crossing, not raw AP.** The parent study already uses Normalized
   Performance Drop. Relative degradation is far more robust to backbone differences than
   absolute accuracy, and floor-crossing is defined *within* a codebase — each method against
   its own ego-only floor.
2. **CoBEVT is the bridge.** It exists in both codebases. Train it here, sweep it here, and
   compare its degradation curve against the parent study's `cobevt`. If the two NPD curves
   agree, the codebases are calibrated against each other and the new methods can be placed
   on the same axes with a stated caveat. If they diverge, that divergence is itself the
   measurement of how much codebase differences contribute — and it must be reported before
   any cross-set claim.

**Train CoBEVT first.** It is the cheapest way to find out whether the comparison is
meaningful at all, and finding out after training three models would be expensive.

## Run order

| Step | What | Gate |
|---|---|---|
| 0 | Download OPV2V train + validate | splits present, checksums recorded in `env/` |
| 1 | Build the second conda env | `import opencood` resolves to the InCoP checkout |
| 2 | Install the overlay | configs generated; loss file present or `--head center_head` chosen |
| 3 | Single-agent pretrain | ego-only floor measured on the OPV2V test split |
| 4 | Train CoBEVT | **bridge gate** — its clean AP and NPD curve vs. the parent study's `cobevt` |
| 5 | Train Where2comm and CGRF | clean AP sane for both |
| 6 | Inertness gate | `commchannel` disabled ⇒ **bitwise-identical** collated batches, 100 frames |
| 7 | Sweep | same matrix, one process per method |

**Step 6 is not optional.** Bitwise inertness when the channel is disabled is the property
that makes every measured difference attributable to the impairment and nothing else. It was
verified for the OpenCOOD stack; it does **not** transfer for free to a different dataset
class, collate path, and torch version. Re-run `scripts/run_phase2_identity.py` against this
stack before trusting any sweep cell.

## Second arm: multimodal

After the LiDAR-only sweep lands, repeat with `sensor_type: multimodal` /
`core_method: bevfusion_isaac`, which is what CGRF was designed for — LiDAR-only may remove
the complementarity the method exploits, so the LiDAR-only result risks under-representing
it. That arm needs OPV2V camera data and adds a camera impairment path to `commchannel`
(dropping a collaborator must drop **both** modalities coherently, and `_survives_crop`
assumes LiDAR points, so it needs a camera equivalent or an explicit bypass).

The comparison between the two arms is worth having on its own: **does complementarity change
the degradation signature, or only the clean-channel ceiling?**
